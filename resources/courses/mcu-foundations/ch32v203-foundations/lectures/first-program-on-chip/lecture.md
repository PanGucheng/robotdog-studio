## 第一课：认识单片机，让 LED 闪起来 {#introduction}

欢迎来到单片机开发世界。本课程面向零基础初学者，无需提前掌握复杂的模拟数字电路或芯片内部微架构。今天我们只聚焦三个最核心的问题：

1. **单片机是什么？** 它与普通电脑、手里的开发板有什么本质区别？
2. **程序如何跨越虚拟与现实？** 一行 C 代码是怎样驱动物理硬件工作的？
3. **真实单片机开发的工作流是什么？** 怎样经历“修改代码 → 编译工程 → 写入开发板 → 观察硬件”的完整闭环？

在本课结尾，你将亲自动手修改一个关键参数，把程序烧录进真实的开发板中，亲眼见证板载 LED 按照你设定的节奏闪烁。

---

### 1. 认识单片机：装在芯片里的微型计算机 {#what-is-mcu}

想一想身边的电子设备：电饭煲如何精确控温、无人机如何感知姿态平稳悬停、机器马如何协调四肢行走？这些设备虽然形态各异，但背后都有一颗负责运算并实时控制硬件的“大脑”——**单片机**。

单片机在行业中通常被称为 **MCU（Microcontroller Unit，微控制器）**。与日常使用的台式机或笔记本电脑不同：电脑追求通用算力（浏览网页、处理文档、运行大型软件），而单片机则高度专注于**特定目标的实时测量与外设控制**。它将 CPU（计算核心）、内存（RAM）、程序存储区（Flash）以及各类输入/输出外设控制器集成在一颗小小的硅片内，具备体积小、功耗低、通电即运行、成本亲民且能直接连接物理电子元件的特点。

:::concept[微控制器（MCU）]
单片机（MCU）是将计算机的核心部件（CPU、存储器、输入输出外设）全部集成在一颗芯片上的微型计算机，专用于自动化测量与物理外设控制。在日常开发中，单片机与 MCU 常作为同义词使用。
:::

### 2. 单片机与现实世界：输入与输出模型 {#input-output}

单片机本身只是一颗芯片，它之所以能感知并改变现实世界，核心在于它连接的外设可以分为“输入”与“输出”两类：

| 类别 | 角色定位 | 典型器件 | 在机器马系统中的分工 |
| :--- | :--- | :--- | :--- |
| **输入（Input）** | 收集环境物理信号，告诉单片机“发生了什么” | 按键、温度传感器、巡线摄像头、红外测距 | 感知地面黑线偏角、检测前方障碍物距离 |
| **核心处理（MCU）** | 运行逻辑程序，分析数据并作出控制决策 | **CH32V203C8T6**（基于 RISC-V 架构） | 状态机切换、步态解算与 PID 控制算法 |
| **输出（Output）** | 接收控制电平，把计算结果转化为物理动作 | LED 指示灯、蜂鸣器、舵机、直流电机 | 驱动马腿关节摆动、发出蜂鸣报警声 |

无论是今天的单颗 LED，还是后续完整的机器马运动控制，整个系统的核心骨架都可以抽象为：  
`[传感器采集物理信息] → [CH32V203 运行程序计算] → [输出信号驱动舵机或 LED]`。

### 3. 概念辨析：单片机 vs 教学开发板 {#chip-and-board}

初学者最容易将“整块电路板”误认为单片机。请明确区分：

- **单片机（MCU）**：特指开发板中央那颗负责执行指令的黑色核心芯片（本平台使用 **CH32V203C8T6**）。
- **开发板（Board）**：是以单片机为核心，在其外围配套了电源管理、USB 调试通信接口（WCH-Link）、板载按键、LED 和扩展排针的整套学习电路板。

开发板免去了我们从零焊接芯片和供电电路的繁琐过程，让我们能直接专注于软件开发与硬件实验。

:::note[为什么从板载 LED 开始？]
在掌握复杂的电机控制之前，LED 是最完美的硬件“探针”。它的亮灭由单片机引脚输出的高低电平直接决定，能以光信号瞬间反馈给肉眼。观察到 LED 闪烁，即证明你的程序已成功穿透软件层，接管了真实硬件。
:::

### 1. 实验代码剖析：单片机程序的生命周期 {#code-analysis}

在编辑器中打开 `App/Src/experiment.c`，本课实验的核心代码非常精简：

```c
#include "experiment.h"
#include "rhs_teaching_platform.h"

/* 闪烁周期：单位为毫秒 (ms) */
static unsigned int blink_period_ms = 500U;

void RHS_Experiment_Init(void)
{
    RHS_Teaching_InitLed();     // 初始化：配置单片机引脚以准备驱动 LED
}

void RHS_Experiment_Loop(void)
{
    RHS_Teaching_DelayMs(blink_period_ms); // 延时等待指定的毫秒数
    RHS_Teaching_ToggleLed();              // 翻转 LED 状态（亮变灭，灭变亮）
}
```

单片机程序的运行规律与常规电脑控制台程序有两处本质不同：
1. **初始化只执行一次**：`RHS_Experiment_Init()` 在单片机通电复位后最先运行，负责底层外设的准备工作（称为**初始化**）。
2. **业务逻辑无限循环**：单片机设备一旦通电，通常需要不间断持续工作。系统底层会周而复始地调用 `RHS_Experiment_Loop()`，交替执行“等待一段时间”与“改变 LED 状态”，从而形成持续闪烁。

---

### 2. 认识关键参数：闪烁时间 blink_period_ms {#blink-parameter}

在代码第 5 行，我们声明了延时参数：

```c
static unsigned int blink_period_ms = 500U;
```

此时无需深究 `static`（静态修饰）或 `unsigned int`（无符号整型）的语法细节，只需明确：
- 变量名为 `blink_period_ms`，当前保存的数值为 `500`（后缀 `U` 表示该数值为无符号整数）。
- 后续的 `RHS_Teaching_DelayMs(blink_period_ms)` 会读取这个数值作为等待时长。
- 这里使用的时间单位为**毫秒（ms）**，换算关系为：$1000\text{ ms} = 1\text{ 秒}$。因此 $500\text{ ms} = 0.5\text{ 秒}$。

## 从源码到硬件：四步工程闭环与实验验证 {#validation-workflow}

初学嵌入式最容易产生一个困惑：“为什么我在编辑器里改了数字，开发板上的灯却毫无变化？”  
原因在于：**电脑是代码的加工厂，而开发板才是代码的运行地**。从修改代码到产生物理现象，必须完整经历以下四个步骤：

| 步骤阶段 | 执行主体 | 关键动作与目的 | 产物或现象 |
| :--- | :--- | :--- | :--- |
| **1. 编辑保存** | 电脑（编辑器） | 修改源码中的参数（如 `blink_period_ms`） | 磁盘中的 `.c` 文本文件更新 |
| **2. 编译生成** | 电脑（工具链） | 检查语法，将 C 语言翻译为单片机可识别的二进制机器码 | 产生 `.elf` / `.bin` 固件文件 |
| **3. 写入芯片** | 调试器（WCH-Link） | 将编译好的固件通过调试线烧录进 CH32V203 内部的 Flash | 单片机存储区更新并自动复位运行 |
| **4. 观察验证** | 真实硬件（开发板） | 芯片执行新程序，驱动板载硬件动作 | PB8 对应 LED 的闪烁周期发生改变 |

:::pitfall[编译成功 ≠ 已经写入开发板]
在软件中点击“编译通过”，仅仅意味着代码没有语法错误且在电脑上生成了固件镜像，该固件此时仍保存在电脑硬盘中！必须执行 **“写入开发板”**，新程序才会被真正烧录进芯片。
:::

### 1. 动手实践：修改并预测实验现象 {#practice-edit}

现在请动手完成你的第一次修改。在 `App/Src/experiment.c` 中定位到第 5 行，将 `500U` 修改为 `1000U`：

```c
/* 修改前 */
static unsigned int blink_period_ms = 500U;

/* 修改后 */
static unsigned int blink_period_ms = 1000U;
```

**现象预测**：
- 原来每等待 500 毫秒翻转一次状态（亮 0.5s $\rightarrow$ 灭 0.5s $\rightarrow$ 亮 0.5s）；
- 修改为 1000 毫秒后，LED 每次保持亮或灭的时间延长到 1 秒，整体闪烁节奏将明显变慢。

### 3. 对比实验：让 LED 极速闪烁 {#compare-experiment}

如果第一次实验验证成功，可以再进行一次对比验证：将 `1000U` 改为 `100U`，再次执行编译与写入。
- $100\text{ ms} = 0.1\text{ 秒}$；
- 此时 LED 将切换为极快速的急促闪烁。

通过这两次对比，你可以得出确凿的因果结论：**你在电脑编辑器中修改的数字，经由编译与烧录工具链，最终真实控制了物理世界中 LED 的发光节奏。**

## 常见问题排查、思考反思与小结 {#troubleshooting-and-summary}

### 1. 常见问题排查清单 {#troubleshooting}

遇到问题是工程实践的常态。第一课遇到异常时，请按以下清单逐一排查：

- **场景 A：编译报错（Candidate Build 或 Firmware Build 失败）**
  - 第一课仅需修改数字，请核对 `App/Src/experiment.c` 第 5 行是否不小心删除了末尾的分号 `;`，或误改了变量名。
  - 检查数值后是否保留了 `U`，且没有输入中文字符。
- **场景 B：写入成功但 LED 没有明显变化**
  - **检查是否真写入了最新固件**：确认在修改代码后是否重新执行了“编译”，然后才点击“写入”。
  - **检查硬件供电与连接**：确认开发板电源指示灯正常常亮，WCH-Link 排线未松动。
  - **等待时间过长/过短**：确认填写的数值是 100 或 1000，避免数值过大（如几分钟才闪一次）产生“死机”错觉。

:::tip[工程调试黄金法则：单变量控制原则]
硬件实验调试中，切忌一次性修改多处代码或同时改动引脚与算法。**每次只修改一个变量**并观察实际现象，才能准确建立“软件改动”与“硬件反馈”之间的因果映射。
:::

### 2. 想一想：核心概念反思 {#reflection}

实验完成后，请结合实验过程思考以下问题：

1. **单片机和开发板是同一个东西吗？**  
   不是。单片机是中央负责运算的微控制器芯片（CH32V203）；开发板是集成供电、接口与外设的实验基板。
2. **为什么在电脑里保存了代码，开发板不会自动同步更新？**  
   电脑中保存的只是磁盘上的文本文件。必须经过**编译**生成机器码，并通过硬件调试器**写入芯片内部 Flash**，单片机才能加载执行新程序。
3. **怎样证明新代码已经成功运行在芯片上？**  
   通过观察真实硬件外设的物理响应（如 LED 闪烁周期的改变）。

### 3. 本课小结与后续展望 {#summary}

恭喜你完成了嵌入式开发的“第一跑”！在本课中，你掌握了：
- **单片机（MCU）的本质**：集成在芯片上的微型计算机，专注于物理控制。
- **嵌入式核心结构**：单次执行的 `Init`（初始化）+ 无限循环的 `Loop`（主业务循环）。
- **工程开发四部曲**：修改代码 $\rightarrow$ 编译生成 $\rightarrow$ 写入芯片 $\rightarrow$ 硬件观察。

你可能会好奇：为什么调用 `RHS_Teaching_ToggleLed()` 就能让 LED 亮灭？底层到底发生了什么？
